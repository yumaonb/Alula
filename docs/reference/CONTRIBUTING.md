# 规范维护准则

## 给谁看

给 AI 和开发者自己看。AI 需要快速判断"该改哪、怎么改"，开发者需要快速找到规范。

## 三层结构

| 层              | 位置                  | 写什么                                               | 什么时候进上下文                                  |
| --------------- | --------------------- | ---------------------------------------------------- | ------------------------------------------------- |
| **入口 + 规范** | 根目录 `AGENTS.md`    | 项目一句话、命令、**开发规范全文**、目录地图、路由表 | **每次请求自动注入**                              |
| **规则**        | `docs/rules/*.md`     | 文件级触发与独有细节，一篇一个主题，80 行以内        | 不自动加载，照 `AGENTS.md` 的「规则怎么读」主动读 |
| **文档**        | `docs/reference/*.md` | 细节、清单、例子、原因、多步骤操作流程               | 直接读，按需                                      |

判断标准：

- 一句话能说清的规范条款（必须 / 禁止）→ **根 `AGENTS.md` 的「开发规范」节**（自动注入）
- 只在动特定文件时才有意义的细节 / 清单 / 例子 → **规则**
- 需要长篇解释、表格、例子、机制原因 → **文档**
- 需要分步骤、有检查清单的操作流程（新增文章、新增组件、交付前自检、文档同步）→ **写进对应文档的「流程」节**，读那篇文档的人自然读到，不另设载体

**不要重复**：同一件事只在一处讲透，其他地方给链接。规则里塞满细节就等于把文档写进了规则。

## 信息分家（新信息进哪个文件）

三层结构解决「怎么加载」，这张表解决「写进哪个文件」。加信息时先按类型对号入座，不要随手放：

| 信息类型                                                        | 进哪里                                                                                                                                       |
| --------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 契约锚（联动点、跨文件隐式契约、代码组织层面的刻意设计）        | 代码注释：相关文件头部 / 函数处（不另立文档）                                                                                                |
| 坑的拍板：怎么修的、不修、看着像 bug 其实是刻意、排查过不是 bug | `docs/reference/TROUBLESHOOTING.md` 的「决定台账」节                                                                                         |
| 现状清单与原理（组件 / 样式 / 架构 / 内容 / 雷区）              | `docs/reference/` 对应篇                                                                                                                     |
| 必须做 / 禁止做的规范条款                                       | 根 `AGENTS.md` 的「开发规范」节                                                                                                              |
| 文件级触发细节                                                  | `docs/rules/`                                                                                                                                |
| 多步骤操作流程                                                  | 对应文档的「流程」节：`docs/reference/CONTENT.md` / `docs/reference/COMPONENTS.md` / `docs/rules/70-verify.md` / `docs/rules/80-doc-sync.md` |

契约与拍板的边界：

- 契约（联动点、跨文件隐式契约、代码组织层面的刻意设计）随代码注释走：改代码时就在场，不需要文档承载。
- 坑的拍板（不修 / 刻意 / 排查过不是 bug）进 `docs/reference/TROUBLESHOOTING.md` 的「决定台账」节；雷区条目的收录标准见该文件顶部。两处内容不重复，同一件事只讲一处。

## 容易过期的东西不写

- 变更史（「以前是 xxx」）——git log 里有。
- 审计过程、任务状态（待修 / 评审中 / 本次已修）——状态一变文档就错。
- 代码能直接查出的清单（组件、CSS 类、`window` 标记）——看机器生成的 `docs/REGISTRY.md`，不手抄。
- 唯一例外是 `文件:行号` 指针：可以写，但动到对应文件时**同日复核**该行号是否还准，顺手改。

## 为什么这样分层

这几条是开发 agent 的实际加载行为，不是约定；分层就是为了顺着它：

- **`AGENTS.md` 是唯一自动注入的入口。** 它沿「项目根 → 会话工作目录」逐层收集，再加用户全局层，整体注入，有体积预算。所以入口越短，留给正文的额度越多。往深层目录成功执行 `read` / `write` / `edit` 后，该目录新适用的 `AGENTS.md` 会被自动追加——这是唯一接近 globs 的机制。
- **规则与文档不自动加载。** 不认任何 glob 或自动挂载标记，只认 `AGENTS.md`。所以约束必须是「路由表指过去、然后主动读」，没有别的办法。流程写进文档里，只有真的读了那篇文档才占上下文。

## 根目录入口

`AGENTS.md` 是唯一会被自动读取的入口，并承载「开发规范」全文。它随仓库入库（`docs/` 同样入库），换机器或 CI 都能读到。
**新增或删除规则/文档后，必须更新它的路由表。**

功能边界与新增功能的约束集中在 `AGENTS.md` 第 14 节；清单、虚拟入口和组合构建机制集中在 `docs/reference/FEATURES.md`，其他文档只给职责或流程指针。

## 改完代码要同步文档

这是硬要求，不是建议：改了什么就更新哪份文档，对照表在 `docs/rules/80-doc-sync.md`。
需要逐条核对清单时，走该篇「顺手检查」清单。

## 写文档的要求

- 标题清晰，一眼知道讲什么；开头一句话说清目的。
- 层级不超过三级。
- 代码示例只给最典型的，不要给一堆变体。
- 规则用"不要做 xxx"比"应该做 xxx"更容易记住。
- 文档用中文，和代码注释一致。
- 及时删掉过时内容，不要留"以前是 xxx"的历史说明——git log 里有。

## 什么时候写新文档

- 反复被问到的问题 → 规范或 FAQ
- 引入新技术栈或架构决策 → 说明文档
- 发现反复犯同一个错 → 规则约束，或在 `docs/reference/TROUBLESHOOTING.md` 加一条

## 什么时候不写

- 代码本身能说清楚的
- `README.md` 里已经有的
- git log 能查到的
- 一次性操作，不需要持久化的

## 新增文档时必须做的事

1. 在 `docs/reference/index.md` 的"什么时候读哪篇"表和规范结构树里加上
2. 在 `AGENTS.md` 的任务路由表里加上
3. 新增的是**规范条款**（必须 / 禁止）时，直接写进 `AGENTS.md` 的「开发规范」节对应小节，不要另开规则文件
4. 新增的是**规则**（文件级细节）时，还要在 `AGENTS.md` 的「规则怎么读」表里加上触发条件

## 格式化与校验工具

| 文件               | 作用                                                                                  |
| ------------------ | ------------------------------------------------------------------------------------- |
| `.editorconfig`    | 编辑器统一约定：UTF-8、LF、2 空格、文件尾换行                                         |
| `.prettierrc.json` | Prettier 规则：单引号、分号、行宽 100，挂 Astro 与 Svelte 插件                        |
| `.prettierignore`  | 排除 `node_modules/`、`dist/`、`.astro/`、`pnpm-lock.yaml`、`src/content/`、`public/` |

| 命令                | 作用                                        |
| ------------------- | ------------------------------------------- |
| `pnpm check`        | `astro check`：类型与模板诊断，必须 0 error |
| `pnpm format`       | Prettier 全量重排                           |
| `pnpm format:check` | 只检查是否已格式化，不写入；适合以后接 CI   |

`pnpm format` 会把仓库里所有非忽略文件重写一遍，产出纯格式差异，所以必须单独提交，不要和功能改动混在一起。文章正文（`src/content/`）与 `public/` 特意排除，避免 Prettier 重排 Markdown 表格与代码块。

> 注意：`docs/` 不在 `.prettierignore` 里，`pnpm format` 会重排本目录的 Markdown。这是可接受的（表格与代码块会重排），但改动后要确认路由表里的路径没被改坏。

## 改完代码后

按 `docs/rules/80-doc-sync.md` 同步文档并核对清单，再按 `docs/rules/70-verify.md` 完成验证；规范与暂缓条件见 `AGENTS.md` 第 9 节。
